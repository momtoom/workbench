# WORKBENCH-V1 컴포넌트 멘탈 모델

## 왜 이 문서가 먼저 필요한가

이전 버전에서 가장 큰 구조적 혼란 중 하나는 "컴포넌트가 무엇인가"에 대한 내부 모델이 충분히 정리되지 않은 상태에서 기능이 계속 쌓였다는 점이다.

겉으로는 컴포넌트처럼 보이지만, 실제로는 다음 개념들이 섞여 있었다.

- 피그마식 컴포넌트
- React 컴포넌트
- 복제된 노드 묶음
- 스타일 override가 가능한 인스턴스
- 내부로 drill-in 가능한 구조

이 상태에서는 다음이 모두 흔들린다.

- source와 instance의 경계
- override의 저장 위치
- 컴포넌트 import의 의미
- nested instance 편집 방식
- variant의 실체
- undo/redo의 복원 단위

V1에서는 먼저 "Workbench에서 컴포넌트란 무엇인가"를 명확히 정의해야 한다.

---

## 핵심 결론

**Workbench의 컴포넌트는 사용자 경험상으로는 피그마처럼 직관적이어야 하지만, 내부 실체는 프론트엔드 컴포넌트 모델을 따라야 한다.**

이 문장이 이 문서의 핵심이다.

즉:

- 사용자는 피그마처럼 쉽게 이해할 수 있어야 한다
- 하지만 내부 구조는 프론트엔드 개발자가 납득할 수 있어야 한다

---

## 이전 버전에서 출발한 직관

이전 버전은 자연스럽게 피그마식 직관에서 출발했다.

그 직관은 매우 유용하다.

사용자 관점에서 컴포넌트는 보통 이렇게 느껴진다.

- 재사용 가능한 UI 묶음이다
- 여러 곳에 배치할 수 있다
- 인스턴스마다 일부를 다르게 쓸 수 있다
- variant를 가질 수 있다
- 필요하면 내부를 들어가 볼 수 있다

이 직관 자체는 버릴 대상이 아니다.
오히려 Workbench UX의 중요한 강점이다.

문제는 이 직관만으로는 실제 프론트엔드의 구현 모델을 충분히 설명하지 못한다는 점이다.

---

## 프론트엔드에서의 컴포넌트 실체

프론트엔드 관점에서 컴포넌트는 단순한 묶음이 아니다.

최소한 다음 개념이 분리되어 있다.

### 1. Source

컴포넌트의 정의 본체다.

예:

- 함수 컴포넌트 정의
- 내부 구조
- 기본 스타일
- variant 정의
- 기본 props 계약

이것은 "원본"이다.

### 2. Instance

source를 사용하는 한 지점이다.

예:

- `<Button />`를 페이지에 배치한 하나의 사용 위치
- `Card`를 어떤 화면에 가져다 놓은 한 인스턴스

instance는 source 자체가 아니다.

### 3. Contract

source와 instance 사이에는 계약이 있다.

예:

- props
- slots
- variant 선택값
- 이벤트/상태 연결

즉 instance는 source를 "복사해서 마음대로 뜯는 물체"가 아니라, source에 값을 주입해 사용하는 경로에 가깝다.

### 4. Override Boundary

instance에서 바꿔도 되는 것과, source를 수정해야만 바뀌는 것이 구분된다.

예:

- 텍스트 라벨 변경: 인스턴스에서 가능할 수 있음
- 컴포넌트 기본 레이아웃 구조 변경: source 수정이어야 함
- variant 선택: 인스턴스에서 가능
- 기본 class 구조 변경: 보통 source 수정

이 경계가 없으면 컴포넌트 모델이 무너진다.

## V1에서의 기본 선언

Workbench V1에서는 컴포넌트를 다음처럼 정의한다.

## 1. 컴포넌트는 "원본 정의 + 사용 인스턴스" 구조다

컴포넌트는 하나의 노드 묶음이 아니다.
컴포넌트는 최소한 두 층으로 존재한다.

- 원본 정의
- 사용 인스턴스

## 2. 인스턴스는 원본과 동일하지 않다

인스턴스는 source의 또 다른 이름이 아니다.
인스턴스는 source를 참조하면서, 일부 계약된 값만 가진다.

## 3. 인스턴스 편집은 언제나 "어디에 저장되는가"가 명확해야 한다

어떤 편집이 발생했을 때:

- source를 바꾸는가
- instance 상태를 바꾸는가
- instance-local override를 바꾸는가

이 세 가지 중 하나로 명확히 귀결되어야 한다.

## 4. source와 instance의 경계는 UX에서 숨길 수 있어도, 내부 모델에서는 숨기면 안 된다

사용자는 "그냥 버튼을 수정한다"고 느껴도 된다.
하지만 시스템은 내부적으로 다음을 알아야 한다.

- 이 수정은 원본 정의 수정인가
- 이 수정은 현재 인스턴스에만 적용되는가
- 이 수정은 허용되지 않는가

---

## Workbench가 재현해야 하는 컴포넌트 경험

Workbench는 피그마처럼 느껴지되, 실제로는 프론트엔드 구조를 따라야 한다.

그 뜻은 아래와 같다.

### 사용자 경험상

사용자는:

- 컴포넌트를 쉽게 배치하고
- 인스턴스를 쉽게 이해하고
- 일부 값을 빠르게 바꾸고
- 필요하면 내부를 탐색할 수 있어야 한다

### 내부 모델상

시스템은:

- source와 instance를 분리하고
- override 경계를 관리하고
- 구조 변경은 source에 귀속시키고
- instance는 계약된 변경만 저장해야 한다

## 이전 버전에서 왜 복잡해졌는가

이전 버전에서는 컴포넌트를 다루다 보니 점점 이런 상황이 생겼다.

### 1. React 컴포넌트처럼 쓰고 싶었다

처음에는 컴포넌트를 "진짜 컴포넌트처럼" 다루고 싶었다.

즉:

- source는 따로 있고
- instance는 그것을 호출/사용하는 식으로 다루고 싶었다

하지만 Workbench는 일반 런타임 빌더가 아니고, 실시간 편집과 구조 탐색이 필요한 도구다.

### 2. 내부 탐색과 편집 요구가 강했다

사용자는:

- 인스턴스를 배치한 다음
- 내부를 drill-in 해서 보고
- 일부를 바꾸고 싶어했다

이 요구는 매우 자연스럽다.

### 3. 그래서 결국 내부 노드를 전개(expand)하는 방식으로 기울었다

source를 호출만 하는 방식으로는:

- 내부 선택
- 내부 hover
- 내부 스타일 편집
- nested instance 탐색

이 어려웠다.

그래서 인스턴스 내부에 source 구조를 펼쳐서 다루는 방식이 생겼다.

### 4. 그런데 전개된 내부 노드는 진실인가, 파생물인가가 불명확해졌다

바로 여기서 복잡성이 폭증했다.

- 펼쳐진 내부 구조가 저장 대상인지
- 단지 preview/편집 표면인지
- 내부 노드 편집이 source를 바꾸는지
- instance override를 만드는지

이 경계가 흔들리기 시작했다.

V1에서는 이 부분을 반드시 정리해야 한다.

## V1의 컴포넌트 모델 원칙

## 원칙 1. Source가 먼저다

컴포넌트의 구조적 진실은 source에 있다.

예:

- 내부 노드 구조
- 기본 스타일 구조
- variant 정의
- 기본 계약

이것들은 source의 책임이다.

## 원칙 2. Instance는 사용 지점이다

instance는 source를 사용하는 위치이며, 다음 같은 상태를 가진다.

- prop 값
- variant 선택값
- instance-local override
- slot 채움값

instance는 source 전체를 소유하지 않는다.

## 원칙 3. Expanded subtree는 파생된 편집 표면이다

인스턴스 내부를 펼쳐 보여줄 수는 있다.
하지만 그것은 원칙적으로 source와 instance 상태로부터 계산된 파생 구조여야 한다.

즉:

- selection 대상이 될 수 있음
- hit-test 대상이 될 수 있음
- inspect 대상이 될 수 있음
- 하지만 저장의 최종 귀속은 source 또는 instance로 환원되어야 함

## 원칙 4. 내부 편집은 항상 귀속 대상이 있어야 한다

인스턴스 내부 노드를 건드렸다고 해서, 그 수정이 자동으로 정당한 것은 아니다.

항상 다음 중 하나여야 한다.

- source 수정
- instance override 저장
- 허용되지 않음

이 셋 외의 모호한 편집 경로는 금지해야 한다.

## 원칙 5. Nested instance도 동일 규칙을 따른다

2중, 3중 중첩 컴포넌트라 해도 예외 규칙을 만들지 않는다.

항상:

- 현재 선택 노드의 owner instance는 무엇인지
- 이 편집의 저장 주체는 누구인지
- source와 instance 중 어디에 귀속되는지

를 계산해야 한다.

## V1에서 컴포넌트가 가져야 할 최소 구조

구현 세부는 나중에 정하더라도, 개념상 컴포넌트는 아래 구조를 가져야 한다.

### 컴포넌트 Source

- 컴포넌트 ID
- 이름
- source root tree
- 기본 스타일 정의
- props 계약
- variant 정의
- slots 정의

### 컴포넌트 Instance

- instance ID
- origin component reference
- propValues
- variantSelection
- slot content / slot mapping
- instance-local override

### 파생 Expanded View

- source + instance 상태로부터 계산
- selection/preview용
- 최종 저장 진실 아님

## Workbench UX에서 어떻게 느껴져야 하는가

사용자에게는 다음처럼 느껴지는 것이 좋다.

### 1. 배치할 때

"컴포넌트를 끌어다 쓴다"

### 2. 값 바꿀 때

"이 인스턴스의 설정을 바꾼다"

### 3. 원본을 고칠 때

"컴포넌트 자체를 편집한다"

### 4. 내부를 볼 때

"인스턴스 내부를 탐색한다"

### 5. 내부를 수정할 때

시스템은 조용히 다음을 판단해야 한다.

- 이건 원본 수정인가
- 이건 인스턴스 override인가
- 이건 허용되지 않는가

즉 UX는 부드럽게, 내부 모델은 엄격하게 가야 한다.

## V1에서 하지 말아야 할 것

## 1. 인스턴스를 사실상 원본 복사본처럼 다루기

겉으로는 source/instance라고 해놓고, 내부적으로는 거의 복사본처럼 운영하면 다시 같은 문제가 생긴다.

## 2. expanded subtree를 저장 진실처럼 취급하기

이건 매우 위험하다.

expanded subtree는 편집 표면일 수는 있어도, source/instance 경계를 대체하면 안 된다.

## 3. panel이 컴포넌트 귀속 규칙을 직접 들고 있기

Inspector나 Preview가 각자 "이건 source에 저장", "이건 instance에 저장" 같은 로직을 가지면 다시 아키텍처가 무너진다.

귀속 판단은 공통 서비스로 올라가야 한다.

## 4. nested instance마다 예외 규칙 추가하기

2뎁스, 3뎁스 중첩마다 보정 분기를 쌓으면 결국 유지할 수 없게 된다.

처음부터 owner/source/instance 귀속 모델로 풀어야 한다.

## 이 문서가 이후 문서에 주는 영향

이 문서를 바탕으로 이후 문서들은 다음처럼 이어져야 한다.

### `STYLING-PHILOSOPHY`

- 스타일은 source의 기본 구조와 instance의 예외 수정으로 나뉘어야 한다
- class 중심 워크플로우를 source/instance 모델 위에 얹어야 한다

### `SOURCE-OF-TRUTH`

- source tree
- instance state
- expanded view
- code projection

이 네 층의 관계를 확정해야 한다.

### `IDENTITY-RULES`

- source identity
- instance identity
- expanded node identity
- style anchor identity

를 분리해 정의해야 한다.

## 최종 정리

Workbench V1의 컴포넌트는:

- 피그마처럼 쉽게 느껴져야 하지만
- 실제로는 프론트엔드 컴포넌트의 원본/인스턴스 구조를 따라야 한다

그리고 인스턴스 내부를 보여주더라도:

- 그 내부 구조는 편집 표면일 수는 있어도
- 저장 진실은 source와 instance 상태로 환원되어야 한다

한 문장으로 줄이면:

**컴포넌트는 "복사 가능한 노드 묶음"이 아니라, "원본 정의와 사용 인스턴스가 분리된 구조"로 모델링되어야 한다.**
