# WORKBENCH-V1 스타일링 철학

## 왜 이 문서가 필요한가

이전 버전에서 스타일 시스템이 복잡해진 가장 큰 이유는 "스타일을 어떻게 조직할 것인가"보다 "스타일을 어떻게 안정적으로 특정 노드에 붙일 것인가"가 먼저 풀렸기 때문이다.

그 과정에서:

- 노드 UUID는 계속 바뀌고
- CSS는 특정 노드를 찾아야 했고
- 추적은 자주 실패했고
- 결국 `WBID`를 만들어 노드가 자기 CSS를 찾게 만들었고
- 그 결과 스타일 시스템이 점점 per-node CSS 중심으로 기울었다

이 흐름은 이해할 수 있는 진화였다.
하지만 V1에서는 이 문제를 더 높은 수준에서 다시 정리해야 한다.

---

## 핵심 결론

**Workbench의 스타일 시스템은 "노드마다 CSS를 붙이는 시스템"이 아니라, "프론트엔드 개발자가 class를 만들고 재사용하고 override하는 과정을 시각적으로 재현하는 시스템"이어야 한다.**

이 문장이 이 문서의 핵심이다.

---

## Workbench가 따라야 하는 인간의 스타일링 워크플로우

실제 프론트엔드 개발자는 보통 이렇게 일한다.

1. 공통 스타일 구조를 먼저 만든다
2. class 또는 재사용 가능한 스타일 단위를 만든다
3. 여러 노드/컴포넌트에 재사용한다
4. variant나 상태별 스타일을 나눈다
5. 정말 필요한 경우에만 개별 override를 만든다

즉 기본은:

- 재사용
- 공유
- 의미 있는 naming
- 구조적 스타일 계층

예외만 개별 패치다.

V1은 이 구조를 재현해야 한다.

---

## 이전 버전에서 생긴 문제를 정확히 다시 정의하기

이전 버전의 본질 문제는 orphan CSS 누적만이 아니었다.
더 근본적인 문제는 아래였다.

### 1. 노드 수와 CSS rule 수가 너무 강하게 연결되었다

노드가 100개면 CSS anchor도 100개, 스타일 rule도 거의 100개가 되는 방향으로 기울었다.

이 구조는 정확한 targeting에는 유리하지만, 인간이 작성하는 프론트엔드 스타일 구조와는 거리가 있다.

### 2. Anchor와 Style Storage가 사실상 같은 층으로 묶였다

`WBID`는 원래 anchor에 가까운 개념인데, 실제로는 스타일 저장 단위까지 같이 떠맡게 되었다.

그 결과:

- 특정 노드를 찾는 문제
- 스타일을 어디에 저장할지
- 스타일을 어떻게 재사용할지

이 세 문제가 한 값에 묶여 버렸다.

### 3. 스타일 편집의 기본 대상이 "노드"가 되어버렸다

실제 프론트엔드 워크플로우에서는 스타일 편집의 기본 대상이 꼭 노드일 필요가 없다.

더 일반적인 대상은:

- class
- 컴포넌트 기본 스타일
- variant 스타일
- token 기반 값
- 예외적 instance override

인데, 이전 버전에서는 노드 자체가 지나치게 중심이 되었다.

---

## V1의 스타일링 원칙

## 원칙 1. 스타일의 기본 단위는 재사용 가능한 구조여야 한다

스타일 시스템의 기본은 다음이어야 한다.

- class
- component base style
- variant style
- token binding
- preset / recipe

노드 직접 스타일은 예외적 경로여야 한다.

새 페이지나 디자인 시안을 Codex가 작성할 때도 같은 원칙을 적용한다. JSX의
inline `style={{ ... }}`는 기본 구현 경로가 아니며, 먼저 컴포넌트 prop,
variant, named component, 또는 Inspector가 인식할 수 있는 token binding으로
표현해야 한다. 토큰으로 표현 가능한 값은 raw CSS 문자열 대신 collection과
token id가 보존되는 바인딩으로 남겨야 한다.

단, 컴포넌트 prop을 CSS 롱핸드의 대체 경로로 늘려서는 안 된다. `border-left`,
`padding-top`, `margin-inline` 같은 세부 시각 속성을 컴포넌트 API로 계속
추가하면 컴포넌트가 Inspector를 우회하는 두 번째 스타일 시스템이 된다.
컴포넌트 prop은 의미 있는 component semantics, variant, 또는 이미 합의된 layout
primitive에 한정하고, 세부 visual override는 Inspector의 style/token layer가
담당해야 한다.

## 원칙 2. 노드를 찾는 키와 스타일을 저장하는 단위는 분리되어야 한다

노드를 안정적으로 가리키는 anchor는 필요할 수 있다.
하지만 anchor가 스타일 시스템의 주인공이 되면 안 된다.

즉:

- anchor는 내부 targeting용
- style storage는 사용자/개발자 워크플로우용

으로 역할이 갈라져야 한다.

## 원칙 3. 사용자가 편집하는 것은 "스타일 대상"이어야 한다

인스펙터에서 스타일을 바꿀 때 시스템은 다음 중 어디에 적용하는지를 알아야 한다.

- 이 노드만
- 이 class 전체
- 이 컴포넌트 기본 스타일
- 이 variant 스타일
- 이 인스턴스에만 적용되는 예외 override

즉 편집 대상은 항상 "노드"가 아니라 "스타일 레벨의 대상"이 되어야 한다.

## 원칙 4. per-node override는 존재할 수 있지만 기본 경로가 되어선 안 된다

Workbench는 직접 만지는 감각이 중요하므로 개별 override 기능은 필요하다.

하지만:

- 모든 편집이 per-node CSS로 떨어지면 안 되고
- 기본 경로는 공유 가능한 스타일 구조여야 하며
- per-node override는 예외여야 한다

## 원칙 5. 토큰은 스타일 시스템의 최하위 값 계층이 아니라 재사용 계층의 일부여야 한다

토큰은 단순한 값 저장소가 아니다.
스타일의 공유와 일관성을 가능하게 하는 핵심 계층이다.

즉 스타일 시스템은 대략 다음 층으로 생각할 수 있다.

- token
- style recipe / class
- component base style
- variant style
- instance / node override

---

## V1에서 스타일 시스템이 가져야 할 층

## 1. Token Layer

색상, 간격, 반경, 타이포 등 공통 값의 정의 계층.

역할:

- 값의 일관성 보장
- 글로벌 변경 가능성 확보

## 2. Shared Style Layer

재사용 가능한 class, recipe, preset, utility 묶음.

역할:

- 공통 스타일 재사용
- 의미 있는 스타일 구조 형성

## 3. Component Base Style Layer

컴포넌트 source에 귀속되는 기본 스타일.

예:

- Button의 기본 구조 스타일
- Card의 기본 layout

## 4. Variant Style Layer

variant나 상태에 따라 갈라지는 스타일.

예:

- `variant=primary`
- `size=lg`
- `state=active`

## 5. Local Override Layer

정말 예외적으로 특정 instance 또는 특정 노드에만 붙는 수정.

이 층은 존재할 수 있지만, 상위 층보다 우선해선 안 된다.

---

## `WBID`의 V1 해석

V1에서도 anchor 개념 자체는 필요할 가능성이 높다.
하지만 그 의미를 축소해서 명확히 해야 한다.

### `WBID`는 무엇인가

- 노드를 안정적으로 targeting하기 위한 내부 anchor
- selection / preview / local override routing에 사용할 수 있는 키

### `WBID`가 아닌 것은 무엇인가

- 스타일 시스템의 중심 개념
- 사용자에게 보이는 class 철학
- 모든 identity를 대체하는 값

즉:

**`WBID`는 스타일 시스템의 주인공이 아니라, 내부 보조 anchor여야 한다.**

---

## 인스펙터가 앞으로 달라져야 하는 점

이전 버전의 인스펙터는 사실상 "이 노드에 어떤 CSS를 붙일까"에 많이 가까웠다.

V1에서는 인스펙터가 더 명확한 선택지를 가져야 한다.

예시:

- 현재 노드만 수정
- 연결된 class 수정
- 컴포넌트 기본 스타일 수정
- 현재 variant 스타일 수정
- 현재 인스턴스에만 override

즉 편집 UI는 "속성 편집기"이면서 동시에 "스타일 귀속 선택기"가 되어야 한다.

---

## V1에서 하지 말아야 할 것

## 1. 노드 수와 스타일 rule 수를 1:1로 고정하는 발상

이건 구현상 쉬울 수는 있지만, 장기적으로는 인간의 스타일링 워크플로우와 맞지 않는다.

## 2. anchor를 class 철학 자체로 오해하기

내부 anchor는 필요할 수 있다.
하지만 그걸 그대로 user-facing 스타일 구조로 삼으면 안 된다.

## 3. 모든 스타일 편집을 local patch로 축소하기

그렇게 되면 재사용 시스템이 무너지고, 결국 Workbench는 확장 가능한 도구가 아니라 노드 패치 머신이 된다.

## 4. token을 단순 값 치환으로만 보기

토큰은 스타일 재사용 계층 전체와 함께 설계되어야 한다.

---

## 최종 정리

Workbench V1의 스타일 시스템은:

- 내부적으로는 anchor를 사용할 수 있지만
- 사용자 경험과 코드 출력 철학은 class 중심이어야 하며
- 기본은 재사용 가능한 스타일 구조,
- 개별 노드 override는 예외여야 한다

한 문장으로 줄이면:

**스타일의 기본은 "이 노드만 꾸민다"가 아니라, "재사용 가능한 스타일 구조를 만들고 필요한 곳에 적용한다"여야 한다.**
